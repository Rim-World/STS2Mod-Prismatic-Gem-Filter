本文记录 0.0.5 施工时验证过的三件事：为什么剔除初始牌与先古牌、多人限定卡怎么归属、配置重置为什么不用 RitsuLib 自带的迁移框架。

## 一、初始牌与先古牌不进入发牌候选

用户说「各职业的初始牌和先古牌本来就不会出现在正常的发牌流程中」。对应游戏里的稀有度是 `Basic`（基础）与 `Ancient`（先古）。

中文名取自 `4.STS2-113.1Reference/localization/zhs/gameplay_ui.json`：

```
"CARD_RARITY.BASIC": "基础",
"CARD_RARITY.ANCIENT": "先古",
```

证据在 `4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Factories/CardFactory.cs`。战斗奖励的抽牌只走 `CreateForReward`，它的两条分支都排掉这两种稀有度：

| 位置 | 分支 | 写法 |
|---|---|---|
| `CardFactory.cs:224` | 稀有度均匀取值 | `items = options2.Where(c => c.Rarity != CardRarity.Basic && c.Rarity != CardRarity.Ancient)` |
| `CardFactory.cs:229` 起 | 按稀有度概率取值 | 先取 `allowedRarities` 集合，再 `RollForRarity`，最后按选中的稀有度过滤 |

第二条分支看似可能掷到 `Basic`，实际不会。`GetNextAllowedRarity`（`CardFactory.cs:266` 起）只往上找：掷到的稀有度不在允许集合里时，调用 `GetNextHighestRarityWithWrapping` 取更高的一档，`None` 才停。`CardRarity` 的枚举顺序是 `None`、`Basic`、`Common`、`Uncommon`、`Rare`、`Ancient`、`Event`、`Token`、`Status`、`Curse`、`Quest`（`MegaCrit.Sts2.Core.Entities.Cards/CardRarity.cs`），所以 `Basic` 会被抬到 `Common`。

结论：棱彩宝石加宽后的候选集合里不可能出现这两种稀有度的卡。名单收录它们只会让界面清单与实际生效范围不一致，过滤结果不变。

## 二、多人限定卡的归属

`MultiplayerConstraint == MultiplayerOnly` 的卡在 0.113.1 共 43 张。原先有 9 张同时列在各自的职业分组与「多人卡牌」组里，靠运行期放行表保证不被职业分组排除。

用户要求「多人模式卡牌不应该重复出现在其它组别的列表里」。9 张从职业分组移出后，其中 4 张（星座、引火、鬼祟、幽冥之界）只在原分组里出现，不补进多人卡牌组就会从模组里消失，因此多人卡牌组由 6 张补到 10 张。

### 门禁写法

`TOOLS/scripts/build-card-group-table.py` 在生成对照表前跑四道核对，任一不过即非零退出、不写盘：

| 序 | 核对 | 依据条款 | 数据来源 |
|---|---|---|---|
| 1 | 每个卡牌标识在 `cards` 表里有对应卡名 | — | `localization/eng/cards.json` |
| 2 | 没有稀有度属于 `Basic`、`Ancient`、`Token`、`Status`、`Curse`、`Event`、`Quest`、`None` 的卡 | SP-023 | 反编译卡牌源码 |
| 3 | 多人限定卡只出现在「多人卡牌」组 | SP-014 | 反编译卡牌源码 |
| 4 | 同时属于两个分组的卡只有大爆炸与铸剑者 | SP-013 | 名单本身 |

后两条的判定键是类名，不是卡牌标识，因为反编译源码按类名分文件。第 4 条的允许集合写成常量 `TWINS`，加双组卡时要在那里登记。

## 三、配置重置

### 为什么不用 RitsuLib 的迁移框架

RitsuLib 0.6.13 自带一套架构版本迁移：`ModDataMigrationConfig` 声明当前版本与最低支持版本，`IMigration` 声明逐步迁移，`MigrationManager.Migrate` 负责跑。版本低于最低支持版本时返回 `RequiresRecovery`，`PersistentDataEntry.Load` 随后调 `MarkCorrupt` 把文件改名成 `settings.json.corrupt`，内存里换成默认值。

这套机制能表达「旧档不要了」，但有两个问题。

第一，落盘时不写版本号。`PersistentDataEntry.Save`（`src/Utils/Persistence/PersistentDataEntry.cs:159` 起）只序列化数据模型，不改写 `schema_version`。版本号只在迁移过程中由 `SetVersion` 写进内存里的 `JsonObject`。若模型里没有对应属性，新建的文件永远没有版本号，每次启动都会被判成 0 版并再隔离一次。

第二，备份回退会把旧档读回来。`FileOperations.ReadTextWithBackupFallback`（`src/Utils/FileOperations.cs:277` 起）在主文件读不到时改读 `文件名 + BackupSuffix`。被隔离的旧档若留下了备份，下次启动会从备份读回旧数据，再走一遍「版本过低 → 隔离 → 默认值」。

结论：重置自己做更直接。字段留在模型里，`Save` 自然把它写进文件，不需要额外机制。

### 实现要点

版本号字段默认 0，`ModSettings.CurrentSchema` 是当前值。`ResetIfOutdated` 在 `Register` 里、`RegisterModSettings` 之前调用，读到的值不等于当前值时整体改写并落盘。

写入用一次 `Store.Modify` 加一次 `Store.Save`。两个 API 的分工是：`ModDataStore.Modify`（`src/Data/ModDataStore.cs:491`）只改内存对象，`Save`（`:512`）才写盘。绑定层的 `ModSettingsValueBinding.Write`（`src/Settings/ModSettings/Binding/ModSettingsValueBindings.cs:98`）同样只调 `Modify`，落盘交给脏绑定的批量回写。重置要保证「下一次启动一定读到新值」，所以显式 `Save`。

### 踩到的坑：属性初始值让缺失字段读成当前版本

第一版把 `SchemaVersion` 写成 `public int SchemaVersion { get; set; } = ModSettings.CurrentSchema;`，认为「文件里没有这个字段就读到 0」。这是错的。

`System.Text.Json` 反序列化时先调用无参构造，再只覆盖 JSON 里出现的属性。文件里没有 `SchemaVersion`，属性就保持初始值，也就是当前版本号。于是判定成了「版本一致」，重置不触发。

证据：第一次无头启动（19:41）的日志里没有 `[settings] reset` 行，`settings.json` 的修改时间仍是 `2026-11-15 23:37:45`，文件内容仍是四个字段，没有 `SchemaVersion`。

修法是两步：模型里不设初始值（缺省就是 0），新建数据的版本号改由注册时的 `defaultFactory` 写入：

```csharp
defaultFactory: static () => new SettingsModel { SchemaVersion = CurrentSchema },
```

这样三种情形都对：旧档缺字段读成 0，触发重置；新建数据由工厂写当前版本，不触发；已有当前版本的档读回当前版本，不触发。

## 四、运行证据

两次无头启动，均为 `--headless`。日志留档在 `8.TEST/0.0.5/`。

第一次（`自检-首次启动重置-godot.log`）：

```
386: [INFO] [PrismaticGemFilter] [settings] reset. schema 0 -> 1, groups=9/13 exemptions=7
388: [INFO] [PrismaticGemFilter] [settings] registered. mode=PrismaticGemOnly master=True groups=9/13 exemptions=7 pages=14
392: [INFO] [PrismaticGemFilter] ready. groups=13 entries=166 exemptions=7 schema=1 patches=1/1
913: [INFO] Wrote 532 bytes to mod_data/PrismaticGemFilter/settings.json in steam remote store
```

第二次（`自检-第二次启动不重置-godot.log`）没有 `reset` 行，`registered` 与 `ready` 两行与第一次相同。`settings.json` 的修改时间停在第一次的 `19:42:43`，说明第二次没有写入。

重置后的 `settings.json` 内容：

```json
{
  "SchemaVersion": 1,
  "Mode": 0,
  "MasterEnabled": true,
  "Groups": { "osty": true, "summon": true, "doom": true, "orb": true, "focus": true,
              "sly": true, "shiv": false, "poison": false, "forge": true, "star": true,
              "arrow": false, "impale": true, "multiplayer": false },
  "Exemptions": [ "doom:NEUROSURGE", "orb:FUSION", "orb:BULK_UP", "forge:BIG_BANG",
                  "star:BIG_BANG", "star:CONVERGENCE", "focus:HYPERBEAM" ]
}
```

原档里的 `"Mode": 0` 与默认取值相同，`Groups` 与 `Exemptions` 为 `null`，因此这次重置在行为上看不出差别。要看出差别得先改几个开关再升级版本，未做。
