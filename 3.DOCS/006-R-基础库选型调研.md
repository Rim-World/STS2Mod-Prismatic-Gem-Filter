## 二、两个库是什么

| 维度 | BaseLib | RitsuLib |
|---|---|---|
| 作者 | Alchyr | OLC（BAKAOLC） |
| 自我定位 | 「帮助并统一**内容添加**」的模组 | 「面向 Mod 作者的共享框架库」 |
| 主要功能面 | 自定义卡牌、遗物、能力、角色、事件、怪物、球、关键词、动态变量、目标类型、Godot 场景与动画、FMOD 音频、声明式配置 | 内容注册、生命周期事件、补丁辅助、持久化与迁移、设置页、本地化、音频、运行时 UI、诊断与兼容 |
| 许可 | MIT | MIT |
| 编译期接入 | NuGet `Alchyr.Sts2.BaseLib` | NuGet `STS2.RitsuLib` |
| 运行时形态 | 独立 mod，含 `.dll` 与 `.pck` | 独立 mod，只含 `.dll`（`has_pck: false`） |
| 运行时依赖 | 依赖另一个 mod `BaseLibCompatibilityHelper` | 无（`"dependencies": []`） |
| 玩家需安装 | **2 个 mod 文件夹**（`BaseLib`、`BaseLibCompatibilityHelper`） | **1 个 mod 文件夹** |
| 文档 | 仓库内 2 篇 + 独立 Wiki 仓库 `BaseLib-Wiki` | 仓库内 26 篇 Markdown + 独立文档站 `sts2-ritsulib.ritsukage.com` |
| 多版本支持 | 单一 DLL，靠反射回退兼容旧签名 | 按游戏 API 版本分别编译，提供 0.107.1、0.111.0、0.113.0 三套兼容模块 |

### BaseLib 的运行时依赖

`BaseLib.json` 声明：

```json
"dependencies": [
  {"id": "BaseLibCompatibilityHelper", "min_version": "0.0.0"}
]
```

发布的 `BaseLib.v3.4.8.zip` 含 5 个文件：

| 文件 | 大小 |
|---|---|
| `BaseLib.dll` | 1,137,664 字节 |
| `BaseLib.json` | 339 字节 |
| `BaseLib.pck` | 138,164 字节 |
| `BaseLibCompatibilityHelper.dll` | 5,120 字节 |
| `BaseLibCompatibilityHelper.json` | 319 字节 |

`BaseLibCompatibilityHelper` 只被一处引用：`NCustomCharacterSelectEntryButton.cs:3` 导入它的 `Intermediary` 命名空间，用于自定义角色选择按钮的适配。该子项目不在公开仓库中（`repos/Alchyr/BaseLib-StS2/contents/BaseLibCompatibilityHelper` 返回 404），只在发布包里出现。

结论：玩家为了用 BaseLib，必须安装 2 个 mod。本项目的模组若依赖 BaseLib，安装链变成 3 个 mod。

## 三、本项目需要什么

需求来自 `1.PRD` 与 `6.SPEC`。

| 序 | 能力 | 来源 | 判定标准 |
|---|---|---|---|
| 1 | 在 `CardCreationOptions.GetPossibleCards` 上加后置补丁 | ADR-001、P3 | 补丁能生效，并能读取该方法的返回值 |
| 2 | 补丁失败时可降级，不使游戏崩溃 | SP-011 | 目标方法不存在时不抛未捕获异常 |
| 3 | 13 个开关的设置界面 | RQ-003、SP-012 | 设置页内可见、可点击 |
| 4 | 开关与豁免清单的持久化 | SP-007、SP-015 | 重启后保持 |
| 5 | 设置界面文案的中英文本地化 | PRD 用语、工坊发布 | 切换语言后文案跟随 |
| 6 | 三个游戏版本可用 | RQ-004、SP-008 | 0.107.1、0.111.0、0.113.1 都能加载并生效 |
| 7 | 按卡牌逐条开关的豁免界面 | RQ-009、SP-013 | 能列出某大类的全部成员并逐张勾选 |

本项目**不需要**的能力：新增卡牌、遗物、药水、角色、事件、关键词、动态变量、目标类型、Godot 场景、动画、音频、随从。

## 四、能力对照

| 需要 | BaseLib | RitsuLib |
|---|---|---|
| 1 补丁 | 无面向使用者的补丁框架。仓库 `Patches/` 只有 1 个内部补丁 `PostModInitPatch.cs`。使用者自己写 Harmony | 有。`RitsuLibFramework.CreatePatcher` + `IPatchMethod` + `ApplyRequiredPatcher` |
| 2 补丁失败降级 | 无。使用者自己 try/catch | 有。`ModPatchTarget(..., ignoreIfMissing: true)` 与 `IsCritical` 标志 |
| 3 设置界面 | 有。继承 `SimpleModConfig`，静态属性自动生成控件 | 有。`RegisterModSettings` + builder |
| 4 持久化 | 有。配置自动读写 | 有。`ModDataStore` + `SaveScope` + 迁移 |
| 5 本地化 | 有。条目进游戏的 `settings_ui` 表，由 `CustomLocTableManager` 合并 | 有。`I18N` + `CreateModLocalization` |
| 6 三版本 | 单一 DLL，靠 `BetaMainCompatibility` 反射回退。不给使用者提供版本门控工具 | 有。按 API 分别编译，运行时自动选模块 |
| 7 逐卡开关界面 | 有基础件：`Create*Option`、`CreateRaw*Control`。条目需自己循环生成 | 有基础件：`AddList`、`AddDynamicChoice`、`AddCustom`、`AddSubpage` |

第 1、2 项是两个库差距最大的地方。本项目全部工作都是「改一条发牌链路」，不是「加内容」，所以 BaseLib 的主要能力面（内容添加）对本项目没有用处。

## 五、决定性差异

### 5.1 多版本支持

本项目要支持 0.107.1、0.111.0、0.113.1 三个版本（RQ-004）。

**RitsuLib** 在构建脚本里直接列出三个目标：

`build/RitsuLib.Compatibility.props:3-6`

```
<RitsuLibCompatTargets>0.113.0;0.111.0;0.107.1</RitsuLibCompatTargets>
<RitsuLibLatestApiCompat>0.113.0</RitsuLibLatestApiCompat>
<RitsuLibLatestGameVersion>0.113.0</RitsuLibLatestGameVersion>
<RitsuLibSharedApiCompat>0.107.1</RitsuLibSharedApiCompat>
```

v0.6.13 的发布资产里，三个版本各有独立产物：

| 资产 | 用途 |
|---|---|
| `STS2.RitsuLib.0.6.13.github.zip` | 面向 0.113.0 API |
| `STS2.RitsuLib.Compat.0.107.1.0.6.13.github.zip` | 面向 0.107.1 API |
| `STS2.RitsuLib.Compat.0.111.0.0.6.13.github.zip` | 面向 0.111.0 API |
| `STS2-RitsuLib.0.6.13.variant-pack.zip` | 一个目录同时覆盖三个版本 |

变体包的选择逻辑在 `components/loader/BundleLayout.cs:44-48`：取「不高于宿主版本的最高兼容目标」。所以游戏 0.113.1 会选 0.113.0 模块，0.111.0 选 0.111.0 模块，0.107.1 选 0.107.1 模块。

**BaseLib** 只有一个 DLL。跨版本靠 `Utils/BetaMainCompatibility.cs` 中的反射封装：

- `CardSelectCmd.Selector` → `RunManager.CardSelectorStack`（`BetaMainCompatibility.cs:76-95`，注释写「versions above 111」）
- `StartRunLobbyPlayer` → `LobbyPlayer`（`BetaMainCompatibility.cs:138-155`，注释写「107 -> 110 rename」）
- `IsUsingController` → `IsUsingDirectionalNavigation`（`BetaMainCompatibility.cs:129-136`）

这套机制解决的是 BaseLib 自己要调用的旧签名，不对外提供「某个目标方法在本版本是否存在」的查询工具。用 BaseLib 写多版本模组时，版本判断仍要自己写。

`BaseLib.json` 声明 `"min_game_version": "0.107.1"`。游戏只把该字段当作下限校验，见 `TMP/0.0.1/调研-反编译/game/ModManager.cs:706-714`。所以它表示「可以在 0.107.1 及以上加载」，不表示「在 0.107.1 上功能完整」。本条为**未验证**：BaseLib 在 0.107.1 上的实际行为没有实测。

### 5.2 补丁失败处理

SP-011 要求「某版本缺少某开关依赖的类型或标签时，该开关表现为无效，其余开关照常工作」。

RitsuLib 的补丁声明支持逐目标标记：

```csharp
public static ModPatchTarget[] GetTargets() =>
[
    new(typeof(CombatRoom), "OnEnter"),
];
```

来源：`docs/pages/guide/patching-guide.md`。同一篇文档写明 `ignoreIfMissing: true` 只用于可选的兼容目标，`IsCritical` 用于区分「补丁失败就停用模组」与「补丁失败只停用该功能」。这与 SP-011 的要求直接对应。

BaseLib 没有对应机制。用 BaseLib 时，SP-011 要自己实现。

### 5.3 安装负担

| 方案 | 玩家需安装的 mod 数 | 说明 |
|---|---|---|
| 本模组 + RitsuLib | 2 | RitsuLib 单目录，无 pck，无额外依赖 |
| 本模组 + BaseLib | 3 | BaseLib 依赖 `BaseLibCompatibilityHelper` |
| 本模组 + 两个库 | 4 | 多装的 BaseLib 对本模组无功能贡献 |
| 本模组 + 不用库 | 1 | 设置界面、本地化、补丁降级全部自己实现 |

### 5.4 同类模组的先例

调研对象 SplashExclusion（创意工坊 `3755773515`）与本项目的工作方式最接近：都在发牌或生成链路上做过滤，都提供逐项开关。

它的工程文件只引用 RitsuLib 的三个程序集：

`TMP/0.0.1/调研-反编译/splash/SplashExclusion.csproj`

```xml
<Reference Include="STS2-RitsuLib.Shared" />

```

它的入口用 RitsuLib 的三项能力：`Store.Register` 持久化、`RitsuLibFramework.SubscribeLifecycle` 生命周期、`RitsuLibFramework.RegisterModSettings` 设置页。见 `SplashExclusionMod.cs:170`、`:174`、`:184`。没有引用 BaseLib。

这是直接可对照的先例：同类模组选了 RitsuLib 单依赖。

### 5.5 设置界面的动态条目

RQ-009 要求「豁免清单须可增删」，SP-013 要求按大类记录豁免。界面要能列出某个大类的全部成员（灾厄牌 14 张、球牌 30 张、星牌 32 张）。

BaseLib 的 `SimpleModConfig` 以静态属性为条目来源，控件在编译期确定。要生成按数量变化的卡片勾选列表，需要用 `CreateRaw*Control` 自己循环创建行，并处理焦点链（`SetupFocusNeighbors`）。文档 `docs/utilities/config-advanced.md` 的「Adding custom controls」一节说明这条路可用，但属于自己搭。

RitsuLib 提供 `AddList`、`AddDynamicChoice`、`AddSubpage`、`AddCustom`（`docs/pages/guide/mod-settings.md` 控件表）。动态条目是既有设计目标，不需要额外搭建。

两者都能做，差别在自建工作量。

## 六、外联与隐私

RitsuLib 含两个会联网的子系统。两个都受开关控制，但需要在发布说明中如实告知玩家。

| 子系统 | 行为 | 默认状态 | 证据 |
|---|---|---|---|
| 遥测 | 首次进主菜单时弹同意提示。同意后才投递 | 需玩家同意 | `src/Telemetry/Integration/TelemetryConsentPromptCoordinator.cs:10-36`、`:117-131` |
| 更新检查 | 请求 `https://sts2-ritsulib.ritsukage.com/ritsulib-update.json` | 受 `RitsuLibSettingsStore.IsUpdateCheckEnabled` 控制 | `src/Updates/RitsuLibUpdateCheckService.cs:19-20`、`:35` |

BaseLib 的发布包与源码中没有发现联网模块。

本模组自身不采集任何数据。玩家安装 RitsuLib 后看到的遥测同意提示来自 RitsuLib，不是本模组。

## 七、四个方案比较

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 只依赖 RitsuLib | 补丁降级、设置页、持久化、本地化、三版本变体全部现成；有同类先例 | 玩家多装 1 个 mod；跟随 RitsuLib 升级；需要披露其遥测与更新检查 | **采用** |
| 只依赖 BaseLib | 设置页与持久化现成；DLL 体积小 | 玩家多装 2 个 mod；无补丁框架与降级机制；多版本要自己判断；主能力面用不上 | 否决 |
| 两个都依赖 | 理论上能力最全 | 玩家多装 3 个 mod；两套设置系统可能各生成一个入口；两套补丁框架叠加，冲突面变大 | 否决 |
| 都不依赖 | 玩家只装 1 个 mod；无第三方风险 | 设置页要自己注入游戏界面并自绘控件；本地化要自己合并进游戏文本表；补丁降级要自己写。设置界面是最易随游戏版本失效的部分 | 否决 |

## 八、遗留风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| RitsuLib 升级破坏兼容 | 版本节奏快，0.6.10 到 0.6.13 在 4 天内 4 个版本 | 在 `mod_manifest.json` 中写明最低版本；升级前跑三版本回归 |
| RitsuLib 补丁面大 | 它自身补丁覆盖存档、联机同步、UI | 本模组只用一个后置补丁，冲突面小；换用前置补丁时需复测 |
| 遥测与更新检查 | 见第六节 | 在工坊说明与 README 中写明数据来源为 RitsuLib，并给出关闭路径 |
| 变体包完整性 | 加载器会校验每个模块的 SHA-256，缺文件即报错 | 发布说明提示玩家整目录安装，不要只复制 DLL |

## 九、对本项目补丁点的影响

调研顺带确认了三个版本的 API 差异，供 P1 使用。

`CardCreationOptions` 在 0.107.1 与 0.111.0 之间改过：

| 项 | 0.107.1 | 0.111.0 及以上 |
|---|---|---|
| `CustomCardPool` 属性 | 有 | 无 |
| `WithCustomPool` | 有 | 无，改为 `WithFilter` |
| `WithCardPools` | `(pools, filter)` 两个参数 | `(pools)` 一个参数 |
| `WithRarityOdds` | 无 | 有 |
| `GetPossibleCards` | 有，`CustomCardPool` 优先分支 | 有，只有卡池分支 |

行号：`1.STS2-107Reference\decompiled\...\CardCreationOptions.cs:169`、`2.STS2-111Reference\...\CardCreationOptions.cs:134`、`4.STS2-113.1Reference\decompiled\MegaCrit.Sts2.Core.Runs\CardCreationOptions.cs:134`。

`GetPossibleCards` 的签名三版一致。调用点在 `CardFactory.cs` 的第 217、217、218 行，三版都是：

```csharp
IEnumerable<CardModel> options2 = options.GetPossibleCards(player).Except(blacklist).ToList();
```

按文件名与字节数比对，0.113.0 到 0.113.1 只有 24 个文件变化（共 3889 个）。`CardCreationOptions.cs`、`CardFactory.cs`、`PrismaticGem.cs`、`CardModel.cs`、`CardPoolModel.cs`、`UnlockState.cs` 都不在其中。该比对只能发现文件新增、删除与字节数变化，字节数相同的内容改动不会被发现。

推论：只打 `GetPossibleCards` 后置补丁，一个 DLL 有望同时服务三个版本。**未验证**，需要 P3 的原型实测。
