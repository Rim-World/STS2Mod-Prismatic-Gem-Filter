# 016-T 悲伤牌的导出与默认豁免

- 建立时间：2026-11-17 01:56

- 对应需求：[RQ-020](../1.PRD/001-项目初期需求.md)
- 版本：0.0.8

## 一、机制

愚者有一套以「悲伤」与「喜悦」为核心的牌。悲伤是衍生牌，属性如下：

| 项 | 值 | 位置 |
|---|---|---|
| 类名 | `Sadness` | `MegaCrit.Sts2.Core.Models.Cards/Sadness.cs` |
| 类型与稀有度 | `CardType.Status`、`CardRarity.Status` | 同上 |
| 费用 | `-1` | 同上 |
| 关键词 | 保留、不可打出 | 同上 |
| 可否战斗内生成 | 否（`CanBeGeneratedInCombat => false`） | 同上 |
| 中文名 | 悲伤（简体）、悲傷（繁体） | `localization/{zhs,zht}/cards.json` 的 `SADNESS.title` |

喜悦（`Joy`）与它成对出现，是这套机制的正面一侧。

别的职业拿不到悲伤的生成源，因此围绕悲伤构筑的牌换人玩几乎一定无效。这是本组收录判据的依据，对应 SP-025 的第四类。

## 二、怎么导出的

悲伤既不是 `CardTag`，也不是 `CardKeyword`，没有可以直接查询的标记，因此按源码引用导出。

```bash
cd "…\4.STS2-113.1Reference\decompiled\MegaCrit.Sts2.Core.Models.Cards"
grep -ln "Sadness" *.cs
```

返回 14 个文件，逐个分类：

| 类别 | 数量 | 处理 |
|---|---|---|
| 悲伤本身 | 1 | 不收。`Status` 稀有度不进入战斗奖励候选，见 SP-023 |
| 多人模式限定卡 | 1 | 不收。按 SP-014 只能留在「多人专属牌」组，而该组按用户 2026-11-16 19:52 的决定不扩充 |
| 愚者池普通卡 | 12 | 收入本组 |

## 四、为什么豁免活跃气氛

用户 2026-11-17 01:42 点名：「除了“活跃气氛”这张牌默认不过滤」。

参数：1 费，稀有，消耗。打出后往手里加 2 张悲伤与 2 张喜悦。它既有负面的一半，也有正面的一半，与其余 11 张「只围着悲伤转」的牌不同。因此它留在组里，但默认勾选豁免，玩家可以自己取消。

这与精神过载、超能光束的处理方式一致，见 SP-021。

## 五、为什么这次必须升架构版本号

豁免清单在 `settings.json` 里是**全量快照**，不是增量。读取路径 `ExemptionBinding` 只在存档里根本没有这个字段时取默认值；有字段就原样读，缺的条目不会自动补。

如果只加组不升版本号，老玩家升级后会发生：新组照常默认勾选，但「活跃气氛」不在他们存档的豁免清单里，于是被一起排除，与用户要求相反。

两条路的取舍：

| 方案 | 后果 |
|---|---|
| 读取时合并缺失的默认豁免 | 玩家此前主动取消过的默认豁免会被恢复，等于覆盖玩家设置 |
| 升架构版本号，整份重置 | 设置回到默认值；代价是玩家的自定义一次清空 |

选后者，与 SP-024 的既定机制一致。实测：`[settings] reset. schema 1 -> 2, groups=11/15 exemptions=8`，日志 `8.TEST/0.0.8/自检-0.0.8重置与名单-godot.log` 第 444 行。

## 六、悲伤与喜悦的边界

本组只收「悲伤侧」。只与喜悦相关、不碰悲伤的牌不在本组。若以后需要过滤喜悦侧，按同样方法查：

```bash
grep -ln "Joy" *.cs
```

结果与本组的 12 张不是同一批牌，需要重新取证，不能想当然认为两张表重合。

## 七、维护要求

1. 游戏版本更新后，重跑第二节的 `grep`，比对返回的类名与本表。新增的愚者池牌要补进来，修掉的牌要移出。
2. 若游戏把「悲伤」改名为别的机制，本组的判据依据要重写，不是只改文案。
3. 若某版本把自贬改成非多人限定卡，它可以进本组，届时补一行名单即可。
4. 豁免清单变化会影响老玩家的行为，改动时按第五节判断是否升架构版本号。
