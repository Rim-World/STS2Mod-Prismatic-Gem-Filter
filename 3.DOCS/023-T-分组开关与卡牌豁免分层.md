# 023-T 分组开关与卡牌豁免分层

- 分类：T（任务知识）
- 时间：2026-11-19
- 范围：0.0.14 的设置模型、实际过滤池、分组说明与三语文案
- 关联：RQ-024、ADR-016、SP-031 至 SP-039、PLANS/015-M

## 一、用户澄清与最终模型

0.0.13 把分组开关与单卡豁免合并为 `Filtered` 集合，分组开关是集合的聚合视图与批量命令。

用户 2026-11-19 澄清：

1. 同一张牌在不同分组之间的状态必须一致，但不是把分组开关与单卡豁免合并。
2. 分组开关独立决定该组是否过滤，不修改单卡豁免名单。
3. 组关闭时主行显示本组贡献 `0/13`；组内跨组牌仍被其他开启组过滤时，追加「本组仍有 x/y 在其他组被过滤」。
4. 只要有一个组开启且该卡未豁免，该卡就必须被过滤。
5. 旧设置重置。

最终模型：

```text
Pool = ⋃ 当前版本可见且已开启的分组（成员） − 全局豁免
```

持久化只有 `Groups` 与 `Exemptions`。`Pool` 只放内存，由 `FilterState.BuildPool` 重算。

## 二、为什么不能只做增量增删

0.0.13 的 `SetGroup` 关闭一组时直接移除该组全部成员。跨组牌如果同时属于另一开启组，也会被移出，违反「只要有一组开启就过滤」。

用户提出的修法是「关闭时先移除，再按其他开启组加回」。这个结果正确。实现改为全量重算，原因：

- 只有 15 组、180 行，重算成本可忽略。
- 组开关、单卡开关、启动、重置、版本切换都走同一入口，不会漏路径。
- 构建新 `HashSet` 后一次性发布，不会暴露 remove/add 中间态。
- 池不落盘，不会出现第三份状态与两份来源打架。

## 三、界面口径

分组说明主行：

```text
定义 · 11 张 · 本组过滤 10/11
```

组关闭：

```text
定义 · 11 张 · 本组过滤 0/11
本组仍有 1/11 在其他组被过滤
```

第二行只在「组关闭且组内至少一张牌因其他开启组进入实际池」时显示。`x` 是跨组过滤数，`y` 是本组成员数。

文案键：

- `pgf.group.filtered`：本组过滤 `{0}/{1}` / `Filtered by this group: {0}/{1}`。
- `pgf.group.otherFiltered`：本组仍有 `{0}/{1}` 在其他组被过滤 / `Still filtered by other groups: {0}/{1}`。

三份 JSON 各 68 个键，`TOOLS/scripts/check-localization-keys.py` 检查通过。

## 五、踩坑

### 首次场景超时

第一次默认场景设 120 秒超时，日志停在场景启动与 Steam 更新检查之后，没有过滤证据。本机 64 个模组加载较慢。把超时提高到 300 秒后，同一场景 45 秒完成。后续场景测试超时必须留足加载时间。

### 设置文件恢复

0.0.14 首次启动会把 schema 5 重置为 schema 6。测试前先复制 `settings.json`，测完恢复原文件，避免把测试设置留给用户。恢复后哈希与备份一致。

### 分组说明的两种“实际”

- 本组贡献：组关时固定 0，用于主行。
- 组内全局实际：可能因其他组大于 0，用于第二行。

把两者混成一个 `x/y` 会让组关闭时出现非零主行，与用户要求不符。
