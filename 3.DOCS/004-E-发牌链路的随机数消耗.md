# 004-E 发牌链路的随机数消耗

- 建立时间：2026-11-15 07:26
- 适用：游戏 0.113.1
- 证据位置：`TMP/0.0.1/调研-反编译/game/CardFactory.cs`、`TMP/0.0.1/调研-反编译/game_full/sts2.decompiled.cs`
- 关联：[RQ-009](../1.PRD/001-项目初期需求.md)、[SP-003](../6.SPEC/001-过滤行为规范.md)、[ADR-001](../4.ADR/001-在候选牌枚举处统一过滤.md)

## 结论摘要

1. 游戏不是「把一个随机数映射到整池的一张牌」。一次取值分两段：先掷稀有度，再在该稀有度的剩余牌里掷下标。
2. 候选表先建好、后抽取。没有「抽到一张、检查、不合格就重抽」的循环。抽到空表时游戏抛异常，不重抽。
3. 因此把牌从候选表里删掉，就等于在源头上不会发它。模组插入的位置正是建表那一步。
4. 一张奖励牌消耗 3 次随机数：1 次稀有度、1 次下标、1 次升级判定。过滤消耗 0 次。

## 一、一次卡牌奖励的完整链路

`CardReward.Populate` 调 `CardFactory.CreateForReward(player, 3, options)`，后者对 3 张牌各调一次私有 `CreateForReward`。单张的流程如下，位置均在 `TMP/0.0.1/调研-反编译/game/CardFactory.cs`：

| 步 | 动作 | 位置 |
|---|---|---|
| 1 | 遗物与模组改写选项，棱彩宝石在这里把卡池并成全角色 | 217 行 |
| 2 | 按选项枚举候选牌：卡池 × 解锁状态 × 多人约束 × 自定义过滤 | 218 行，调 `GetPossibleCards` |
| 3 | 去掉本次奖励已经出现过的牌，避免 3 张重复 | 218 行，`Except(blacklist)` |
| 4 | 过一遍 `IsAllowedInRun` | 219 行 |
| 5 | 掷稀有度 | 229 行，`RollForRarity` |
| 6 | 取该稀有度的牌表，掷下标取一张 | 234、237 行 |
| 7 | 掷是否升级 | 102 行 |

### 第 5 步：稀有度的掷法

`RollForRarity`（245 行）拿一个 `NextFloat()`，与两条阈值比较：

```
稀有度 = 稀有 ?
        罕见 ?
        普通
```

普通战斗奖励（`RegularEncounter`，非苦难点）的阈值是稀有 3%、罕见 37%、普通 60%。苦难点为 1.49%、37%、61.5%。阈值表见 `sts2.decompiled.cs:56483` 起的 `CardRarityOdds`。

战斗奖励走 `Roll`，会推进保底计数：掷到稀有把计数清零重来，其余情况每次加 0.01，上限 0.4。商店与部分事件走 `RollWithBaseOdds`，不动保底计数（`sts2.decompiled.cs:56554` 与 `56608`）。

### 第 6 步：下标的掷法

`Rng.NextItem`（`sts2.decompiled.cs:54404`）：

```
把集合转成数组 → 取长度 n → 若 n 为 0 返回 null → 否则 NextInt(0, n) → 取第 index 个
```

一次整数抽取，一次下标访问。没有循环，没有重试。

`CreateForReward` 在拿到 null 时直接抛 `InvalidOperationException`（240 行）。游戏不靠重抽兜底，所以候选表为空就是坏档式的错误。这也是 SPEC 的 SP-002 要求回退的原因。

## 二、随机数消耗表

| 环节 | 消耗 |
|---|---|
| 掷稀有度 | 1 次 `NextFloat` |
| 掷下标 | 1 次 `NextInt` |
| 掷升级 | 1 次 `NextFloat` |
| 枚举候选表 | 0 次 |
| 我们的过滤 | 0 次 |

一次发牌 3 张，合计 9 次随机数抽取。过滤无论排除多少张牌，都不加也不减这 9 次。

## 三、模组插入点的因果

模组在 `GetPossibleCards`（第 2 步）上做后置过滤。这个函数的返回值被第 3 步的 `Except` 与第 4 步的 `IsAllowedInRun` 各枚举一次，最终落到第 5、6 步。

因果链：被排除的牌不进入第 6 步的数组 → 下标再大也取不到它 → 不存在「先抽到再换一张」。

由此推出两条行为：

- 剩余牌的单张概率升高。例如某稀有度原本 140 张，删掉 20 张后剩 120 张，每张概率由 1/140 变为 1/120。这是过滤的必然结果，不是副作用。
- 稀有度概率不变，除非某个稀有度被整档删空。整档删空时 `GetNextAllowedRarity`（265 行）会向上跳到仍有牌的稀有度；绕回原点则返回 `None`，随后抛异常。实际牌池有 5 个角色加无色池，单档删空不会发生，但代码路径存在。

## 四、两处容易误解的地方

- 候选表被枚举两次：第 3 步的 `Except(blacklist)` 一次，第 4 步的 `ToArray` 一次。因此过滤谓词每张牌跑两次。按 718 条候选实测，单次 11 µs，实际约 22 µs。可在过滤时一次性物化成 `List` 降为一次，属实现优化，不影响行为。
- 第 1 步的钩子对 3 张牌各调用一次，棱彩宝石的并集也因此执行 3 次。游戏没有缓存选项，模组必须自己缓存排除索引，这正是 SP-010 的由来。
