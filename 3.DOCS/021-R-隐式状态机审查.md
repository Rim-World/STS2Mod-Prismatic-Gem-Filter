# 021-R 隐式状态机审查

- 分类：R（审查报告）
- 时间：2026-11-18 20:22
- 范围：`9.SRC/src` 全部源码，重点检查设置、缓存、界面绑定、版本探测与发牌链路中的隐式状态。
- 触发：用户要求「检索模组中所有隐式状态机，排查逻辑不自洽、状态不同步的问题」。
- 状态：历史快照（0.0.13）；2026-11-19 补更正说明，0.0.14 已推翻 S1 与 S4 的「唯一状态」结论。

## 结论

本次审查确认两类真实问题：

1. 设置模型有两个独立真相来源：分组布尔值与卡牌豁免清单。同一张跨组卡的实际过滤结果会随分组层变化，与卡牌层显示不一致。0.0.13 曾改为按卡牌唯一记录，但 2026-11-19 用户澄清该判断有误：分组开关应独立，单卡豁免才跨组共享。0.0.14 改为 `Groups` 与 `Exemptions` 分层，见 [ADR-016](../4.ADR/016-分组开关与卡牌豁免分层.md)。
2. 界面刷新拓扑不完整。旧分组开关是 `Global` 绑定，卡牌开关是 `ExemptionBinding` 的投影。卡牌改动只标记父绑定脏，分组开关不在同一失效链上，跨页显示可能滞后。0.0.13 把分组开关也改为 `FilteredBinding` 的投影；0.0.14 改为分组绑定与豁免绑定各自独立，`GroupDescription` 同时依赖两者。

> 2026-11-19 更正：本报告 S1 与 S4 的「唯一状态」结论只适用于 0.0.13。0.0.14 已恢复分层，分组开关不修改豁免名单；跨组卡状态仍按卡牌唯一记录。当前实现与证据见 `3.DOCS/023-T-分组开关与卡牌豁免分层.md`。

另有三项缓存或发布问题已加固，两项低风险假设保留，四项属于作用域覆盖，不是状态不同步。

## S1 设置状态

**问题。** 旧模型同时保存 `Groups` 与 `Exemptions`。排除规则为「任一勾选可见组包含该卡，且该卡未豁免」。跨组卡在 A 组保留、B 组勾选时，A 页显示保留，实际仍被 B 组排除。这是用户报告的现象。

**修复（0.0.13 历史）。** 唯一状态改为 `Filtered` 集合。分组开关读取「任一张成员在集合内」，写入「全组加入或移出」；单卡开关写入「该卡加入或移出」。分组不再是第二份状态。

默认集合按 `CardGroupTable.Rows` 全表加 `CardGroups.All` 的默认值计算，而不是遍历 `All` 的成员。0.111 的 `All` 已剔除愚者成员；按成员遍历会让玩家切到 0.113 后缺少 22 张默认排除。这是审查中发现的第二个跨版本状态缺口。

**证据。**

- `9.SRC/src/ModSettings.cs` 的 `SettingsModel.Groups`、`SettingsModel.Exemptions` 与快照的 `IsGroupEnabled`、`IsExempt`。
- `9.SRC/src/FilterState.cs` 的 `SetGroupEnabled`、`SetExempt`、`BuildPool`。
- `9.SRC/src/ExclusionTable.cs` 的 `DefaultExcludedKeys` 与 `Build`。

**0.0.14 更正。** 上述 `Filtered` / `IsGroupFiltered` / `SetGroup` 是 0.0.13 的符号，当前源码已删除。现行实现恢复 `Groups` 与 `Exemptions` 两份来源，见 [DOCS/023](023-T-分组开关与卡牌豁免分层.md) 与 [ADR-016](../4.ADR/016-分组开关与卡牌豁免分层.md)。

## S2 设置快照

**问题。** 旧实现用 `_cached` 与 `_cachedVersion` 两个字段发布快照，读取没有内存屏障。写入路径递增 `_version`，但缓存字段直接读写。游戏主线程通常不会触发问题，但这不是可证明的发布语义。

**修复。** `_version` 用 `Interlocked.Increment`，`_cached` 与 `_cachedVersion` 用 `Volatile.Read/Write`；`Invalidate` 同时清空缓存。`FilterIndex` 也改用 Volatile 发布。

**保留风险。** `Build()` 仍允许两个线程同时构建快照。后写入的旧版本快照会因版本号不匹配在下次读取时重建，不会永久生效。游戏侧绑定写入与发牌回调都在主线程，实际触发概率低。若要彻底消除，需要把快照构建和缓存发布放进同一把锁，并调整与 `FilterIndex.Gate` 的锁顺序。

## S3 排除索引

**问题。** `Ensure` 的双检锁只对 `_builtVersion` 做了普通读写。写线程先写 `_excluded`、`_activeGroups`，再写版本号；读线程可能看到新版本号但旧集合。

**修复。** `_excluded`、`_activeGroups`、`_builtVersion` 全部用 `Volatile` 发布。`Invalidate` 只写版本号。

**残留。** `CardCreationPatch.Describe` 先取 `FilterIndex.Get`，再单独读 `FilterIndex.ActiveGroups`。如果两次读取之间设置变化，日志里的 `groups` 与 `removed` 可能来自不同版本。只影响日志，不影响发牌结果。

## S4 界面绑定刷新

**问题。** 旧分组开关用 `ModSettingsBindings.Global` 读写 `model.Groups`，卡牌开关用 `Project` 读写 `ExemptionBinding`。卡牌写入时，RitsuLib 的失效拓扑沿 `Project` 找到父绑定，但找不到另一个 `Global` 分组绑定。分组页的开关与说明可能不刷新。

**修复（0.0.13 历史）。** 分组开关与卡牌开关都改为 `Project<List<string>, bool>`，父绑定同为 `FilteredBinding`。`GroupDescription` 的动态文本也把 `FilteredBinding` 列为刷新依赖。这样卡牌改动会使所有分组开关与说明进入同一失效链。

**证据。**

- `9.SRC/src/ModSettings.cs` 的 `BuildBindings`（0.0.13 历史）：`GroupBindings[id]` 与 `CardBindings[entry]` 都从 `FilteredBinding` 投影。
- `9.SRC/src/ModSettings.cs` 的 `GroupDescription`（0.0.13 历史）：`ModSettingsText.Dynamic(..., FilteredBinding)`。
- RitsuLib `ProjectedModSettingsValueBinding` 的 `ExtraBindingsToMarkDirtyForUi` 指向父绑定；`ModSettingsBindingInvalidationTopology.ExpandClosure` 沿该关系扩展。

**0.0.14 更正。** 分组绑定来自 `GroupsBinding`，单卡绑定来自 `ExemptionsBinding`；`GroupDescription` 同时依赖两者。旧 `FilteredBinding` 已不存在。

## S5 配置架构重置

**问题。** `ResetIfOutdated` 写盘失败时只记日志并继续。旧实现的日志说「沿用存档里的值」，但旧架构的 `Groups` 与 `Exemptions` 在新代码里可能已经失效。

**修复（0.0.13 历史）。** 0.0.13 的模型没有 `Groups` 与 `Exemptions`，旧档读不到 `Filtered` 时 `FilteredBinding.Read` 返回默认集合。重置失败时本次运行按默认筛选状态工作，日志明确写「存档仍可能是旧架构」。

**0.0.14 现状。** `SettingsModel` 恢复 `Groups` 与 `Exemptions`。`ResetIfOutdated` 在 `SchemaVersion != 6` 时把模型整体重写为默认值并落盘一次，不依赖 `FilteredBinding`。0.0.14 的 `reset. schema 5 -> 6` 见 `8.TEST/0.0.14/自检-0.0.14-113设置注册-godot.log`。

**残留。** 若重置失败，玩家本次的修改可能写入一个 `SchemaVersion` 仍为旧值的文件，下次启动再次触发重置。这是持久化失败下的降级，不是状态不同步。

## S6 游戏能力探测

`GameFeatures.HasFool` 是静态只读属性，在类型初始化时执行一次。游戏版本不会在同一进程内切换，因此不需要运行时状态机。检测顺序为类型优先、版本号兜底、最后按含愚者处理，三条路径都有日志。

保留假设：玩家在同一进程内不会替换游戏程序集。

## S7 卡池成员缓存

`CardCreationPatch.OwnPoolEntries` 用 `ConditionalWeakTable<CardPoolModel, HashSet<string>>` 按卡池实例缓存 `AllCardIds`。卡池模型被当作规范单例。

保留假设：卡池成员在进程内不变。若未来有模组在运行期向卡池追加卡牌，这份缓存会漏掉新成员。当前受支持的两个版本与已知模组不触发。

## S8 名单自检

`VerifiedPools` 在核对前先写入标记。若首次核对因异常中断，后续调用会跳过该池的自检。

影响范围：只影响 `[self-check]` 日志，不影响过滤。保留原因：自检是诊断辅助，不应在发牌路径上反复扫描。

## S9 实际发牌的覆盖

以下四项会让「设置层状态」与「本次实际输出」不同。它们不是第二份卡牌状态，而是作用域覆盖：

| 覆盖 | 行为 | 规则 |
|---|---|---|
| 总开关关闭 | 不改变候选集合 | SP-020 |
| 判定模式未命中 | 不进入过滤 | SP-005、SP-019 |
| 候选属于玩家职业卡池 | 不排除 | SP-004 |
| 过滤后为空 | 放弃本次过滤 | SP-002 |

界面上的单卡状态是「设置层是否排除」。实际发牌是否排除还要经过这四道覆盖。审查没有把这类覆盖改成第二份卡牌状态，否则会重新引入状态不同步。

## 保留风险

| 编号 | 风险 | 影响 | 处理 |
|---|---|---|---|
| R1 | 快照并发构建 | 旧快照可能短暂返回，下次读取重建 | 保留；主线程模型下不触发 |
| R2 | `FilterIndex` 日志跨版本 | 日志的 `groups` 与 `removed` 可能不同版本 | 保留；只影响诊断 |
| R3 | 卡池成员运行期变化 | 新成员不在池门控集合 | 保留；当前版本无此行为 |
| R4 | 自检标记提前写入 | 首次异常后不再自检 | 保留；不影响过滤 |
