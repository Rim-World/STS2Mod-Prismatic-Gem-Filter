# 012-T 分组开关、豁免清单与界面本地化的落地

- 建立时间：2026-11-15 23:22
- 状态：历史快照（0.0.4）；其中 184 个卡牌开关与两个排除集合的写法已被 0.0.14 的 180 行、`Groups` + `Exemptions` 分层取代。
- 适用：游戏 0.113.1，RitsuLib 0.6.13
- 关联：[RQ-003](../1.PRD/001-项目初期需求.md)、[RQ-014](../1.PRD/001-项目初期需求.md)、[SP-012](../6.SPEC/001-过滤行为规范.md)、SP-014、SP-020 至 SP-022、[2.PLANS/004-M](../2.PLANS/004-M-分组开关与设置页.md)

## 结论摘要

1. 模组的界面本地化有三条路。游戏内置的模组表合并只能往已有表里加键；要新建自己的表，只能靠 BaseLib 的 `.locale` 或 RitsuLib 的 `I18N`。本项目取后者，三份 JSON 作为嵌入资源打进 DLL。
2. RitsuLib 的 `I18N` 遇到缺当前语言的条目时回退 `eng`。语言代码 `zht` 不被归一化，所以繁体中文会去找 `zht.json`。这正好满足 SP-022 的三分法。
3. `RegisterModSettings` 的配置回调在注册时立即执行并 `Build()`。页面结构写错会在启动日志里立刻暴露，不必等玩家点开设置页。
4. 184 个卡牌开关共用同一个 `List<string>` 父绑定，靠 `Project` 投影成一个个布尔开关。写入时整表替换，缺省值由 `WithDefault` 提供。（0.0.4 历史数字；当前名单 180 行、178 张唯一牌。）
5. 排除集合必须分成两个。合并成一个时，「这张卡是不是多人限定」只能放到逐张循环里判断，SP-014 与 SP-015 的区分也会丢失。（0.0.4 历史结论；0.0.5 起按 ADR-009 删除放行表，排除索引合并为一个集合。）

## 一、模组本地化的三条路

| 路线 | 文件位置 | 能否新建表 | 本项目是否采用 |
|---|---|---|---|
| 游戏内置的模组表合并 | `<模组目录>/localization/<语言>/<表名>.json` | 不能 | 否 |
| BaseLib 的 `.locale` 平铺文件 | `<模组目录>/localization/<语言>.locale` | 能 | 否，[ADR-006](../4.ADR/006-只依赖RitsuLib作为基础库.md) 只依赖 RitsuLib |
| RitsuLib 的 `I18N` | 嵌入资源、文件系统或 pck 里的 `<语言>.json` | 能 | 采用 |

第一条路的限制来自实现顺序。`LocManager.LoadTablesFromPath` 先枚举游戏自带 `res://localization/<语言>/` 目录下的文件名，再对每个文件名调用 `ModManager.GetModdedLocTables` 合并模组的同名文件。模组能提供的只有这些已有表，新建的 `prismatic_gem_filter.json` 不会进入枚举。

证据位置：

- `4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Localization/LocManager.cs:468` — 枚举游戏自带的表文件。
- 同文件 `:495` — 对每个表名合并模组的同名文件。
- `.../MegaCrit.Sts2.Core.Modding/ModManager.cs:972` — 模组表的路径拼法是 `res://{清单 id}/localization/{语言}/{文件名}`。
- 创意工坊里走第二条路的实例：3810696310 与 3816316338 的 `localization/eng.locale`、`zhs.locale`、`zht.locale`。

`res://{清单 id}/` 还需要模组带 `.pck` 才存在。本模组是纯 DLL，`has_pck` 为 false，所以第一条路本来也走不通。

第三条路的关键实现：

- `7.Mod-Sources/STS2-RitsuLib-v0.6.13/src/Utils/I18N.cs:636` — 嵌入资源按 `<资源目录>.<语言>.json` 的清单名读取。
- 同文件 `:557` — 加载顺序是先当前语言、再回退语言。
- 同文件 `:568` — 未指定回退语言时，非英语一律回退 `eng`。

## 二、语言代码 `zht` 不被改写

`I18N.NormalizeLanguageCode` 的匹配表把 `zh`、`zh_cn`、`zh_hans`、`zh_sg` 归一到 `zhs`，没有 `zht` 分支，落到 `_ => text` 原样返回，位置 `I18N.cs:776` 起的 switch 与 `:792` 的默认分支。

后果：游戏语言为 `zht` 时会去找 `zht.json`；为 `jpn`、`deu` 等 15 种语言时找不到对应文件，回退到 `eng.json`。这正是 SP-022 要的三分法，不需要额外写判断。

## 三、设置页的三件工具

### 3.1 多页注册与立即构建

`RitsuLibFramework.RegisterModSettings(modId, configure, pageId)`，`pageId` 缺省等于 `modId`。注册流程是新建构建器、执行配置回调、立刻 `Build()`，位置 `.../Core/ModSettingsRegistry.cs:307-309`。

推论：页面结构的错误（空节、重复条目标识、非法范围）在启动时就会抛异常。本次施工因此可以只靠一次无头启动验证 14 个页面的结构。

### 3.2 子页

1. 子页注册时用 `page.AsChildOf(父页标识)` 声明父子关系。
2. 子页用 `WithSidebarVisibleOnlyWhenActive()`，侧边栏条目只在进入该页时出现，避免 13 个豁免页挤占侧边栏。
3. 父页用 `AddSubpage(条目标识, 标题, 目标页标识, 按钮文本, 说明)` 放跳转行。

### 3.3 一个父值投影出多个开关

父绑定是一个 `List<string>`，元素形如 `doom:NEUROSURGE`。每个卡牌开关是它的一次投影：

```
ModSettingsBindings.Project<List<string>, bool>(
    父绑定, "分组_卡牌", 清单 => 清单.Contains(键), (清单, 勾选) => 改后的新清单)
```

`ProjectedModSettingsValueBinding.Write` 的做法是「读父值 → 用返回的新值写回父绑定」，位置 `.../Binding/ModSettingsValueBindings.cs` 的 `ProjectedModSettingsValueBinding`。所以写回必须返回新对象，不能原地改。

缺省值由 `WithDefault` 的工厂给出。本项目的写法是「清单为 null 表示从未改过，取默认清单」，不需要存档迁移。

## 四、为什么排除索引分两个集合

SP-014 要求多人限定卡不被按标记判定的组排除，SP-015 又允许显式名单组点名排除这类卡。若只建一个集合，求值时无法区分某条目来自哪一类组，只能把「是不是多人限定卡」的判断放进逐张循环。

分成两个集合后的数据流：

| 步骤 | 内容 |
|---|---|
| 建索引 | 对每个已勾选分组，把成员减去该组豁免项，按组类归入标记集合或显式集合 |
| 后处理 | 从标记集合里减掉 9 张多人限定卡 |
| 发牌 | 每张候选牌查两次哈希表，命中任一集合即排除，再走池门控 |

## 五、缺省值的表达方式

`SettingsModel` 的 `Groups` 与 `Exemptions` 都是可空类型。`null` 表示玩家从未改过，此时取代码里的默认值。第一次改动会把整表写入。

这样做换来两件事：新增分组不需要迁移旧存档；默认值调整只改代码，不写迁移脚本。代价是「玩家把清单改回全空」与「玩家从未改过」在存档里都能被区分，因为前者会落一个空列表。

## 六、实测证据

Release 构建 54,272 字节。无头启动一次，日志关键三行：

```
[PrismaticGemFilter.texts] Loaded translations: language='zhs', fallback='eng', entries=51, local=51, fallbackEntries=0, sources=2 (local=1, fallback=1)
[settings] registered. mode=AnyWidenedPool master=True groups=7/13 exemptions=6 pages=14
```
