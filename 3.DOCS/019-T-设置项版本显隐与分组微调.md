## 三、版本显隐的实现

`GameFeatures.HasFool` 的判断顺序：

1. 查 `typeof(CardModel).Assembly.GetType("MegaCrit.Sts2.Core.Models.CardPools.FoolCardPool")`。这是游戏内容本身，最直接。
2. 类型探测抛异常时，读 `ReleaseInfoManager.Instance.SemVer`，`Major > 0` 或 `Minor >= 113` 视为含愚者。
3. 两条都失败时返回 `true`，宁可多显示。

`CardGroups.Build(bool hasFool)` 在 `hasFool` 为假时，过滤 `CardGroupTable.Rows` 里 `Pool == "FoolCardPool"` 的行。`CardGroups.Visible` 只保留成员非空的组。设置页注册、排除索引、张数说明与「同时属于」提示都改用 `Visible`。

0.111 的结果：15 个组里可见 11 个；箭矢、扎穿、悲伤、缺陷四个组成员为空；多人组从 10 张降为 9 张；`COVERING_FIRE` 与 `BLOT_OUT_THE_SKY` 都不在可见名单里。

## 四、为什么先查类型而不是先读版本号

最初写成「先读 `ReleaseInfoManager`，失败再查类型」。在一次性验证程序里，`ReleaseInfoManager` 构造时调用 `Godot.OS.GetExecutablePath()`。验证程序没有加载 Godot 原生库，直接访问违例崩溃，托管 `try/catch` 接不住。

游戏进程里 Godot 已初始化，不会出这个问题。但这个顺序也说明：模组初始化早期就能不依赖 Godot 文件接口完成判断，更稳。改成类型优先后，0.111 与 0.113 都只做一次反射查类型，不碰 `release_info.json`。版本号只在类型探测抛异常时兜底。

## 六、踩到的坑

1. **托管异常接不住 Godot 原生崩溃。** 没有 Godot 原生库时，`Godot.OS.GetExecutablePath()` 是访问违例，不是 `DllNotFoundException`。验证程序里必须避免走到这条路。
2. **0.111 的 `sts2.dll` 有模块初始化器。** 它会在加载时调用 `SentryAutoInit.Init()`。验证程序需要同时提供 `Sentry.dll` 与 `Sentry.Godot.dll`，否则类型初始化直接失败。
3. **无头游戏进程不会总在预期时间退出。** 本轮两次构建的部署警告都来自一个残留的 `SlayTheSpire2.exe`。`taskkill //F` 在 Git Bash 下被当成非法参数，改用 `taskkill -F -IM` 才生效。收工前必须用 `tasklist` 确认没有残留。
4. **`SkipUnchangedFiles` 不解决文件占用。** 游戏进程锁着 `mods/PrismaticGemFilter/PrismaticGemFilter.dll` 时，构建只警告不中断，容易误以为已部署。核对方法是对比 `9.SRC/bin/Release` 与游戏 `mods` 目录两处的 SHA-256。
5. **可见性要改干净。** 改 `CardGroups` 的可见性后，原先依赖 `CardGroups.All` 的三处（设置页注册、排除索引、张数说明）都要一起改。只改一处会留下「组隐藏了但索引还在算」或「张数还是旧值」的假象。
