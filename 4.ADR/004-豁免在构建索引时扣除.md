# 004 豁免在构建过滤索引时扣除

- 状态：提议
- 日期：2026-11-15
- 项目版本：0.0.0
- 相关文件：[ADR-001](001-在候选牌枚举处统一过滤.md)、[ADR-003](003-卡牌分组的判定方式.md)、[SPEC](../6.SPEC/001-过滤行为规范.md)、[DOCS/003](../3.DOCS/003-E-豁免与多人卡取证.md)

## 背景

需求要求在大类内豁免特定卡牌（RQ-009）。用户担心豁免会让判定退回逐卡穷举，拖慢发牌。

约束一：豁免项会随时间增加，用户明确说了「暂时先想到这么多」，因此不能写死成代码分支。

约束二：`BigBang` 与 `TheSmith` 同属铸剑与星两类（`TMP/0.0.1/卡牌名单/卡牌分组名单.csv`）。若把豁免当全局集合处理，两类开关会互相抵消，且结果随求值顺序变化。

约束三：多人模式下，多人限定卡必须照常出现在棱彩宝石的发牌里（RQ-010）。43 张 `MultiplayerOnly` 卡牌中有 9 张落在被筛大类内，见 [DOCS/003](../3.DOCS/003-E-豁免与多人卡取证.md) 第三节。

约束四：SPEC 已要求过滤集合只求一次并缓存（SP-010），发牌路径上不得重复求值。

## 决策

豁免按「大类 → 卡牌 id 集合」存储，不作为运行时的判定分支。过滤索引在设置变更后重建一次，构建规则为：

```
对每个处于勾选状态的大类 C：
    对 C 的每张卡 K：
        若 K 属于多人限定卡，跳过
        若 K 在本类豁免集合中，跳过
        将 K 写入排除索引
```

运行时的判定只有一句：候选牌的 id 是否在排除索引里。

## 备选方案

**运行时逐类判断**：对每张候选牌遍历 12 个大类，命中后查该类的豁免表。否决理由：实测 209.31 µs，是决策方案的 8.2 倍；且每张牌都要走 12 次分支，判定逻辑分散在发牌路径上。

**全局豁免表**：一张卡只要被豁免就永不排除。否决理由：与用户的「从大类中豁免」表述不符，且无法表达「这一类里我要它、那一类里我不要」；`BigBang` 的双重归属会让语义更混乱。

**每次发牌重建索引**：否决理由：违反 SP-010，且索引构建也要 15.24 µs，白白重复。

**用配置文件让用户写 Lua 或表达式**：否决理由：用户明确说过不要额外格式，且会引入脚本执行风险。

## 后果

**获益**

- 豁免数量增加不影响运行时开销。索引就绪后单次过滤 10.91 µs，与无豁免的 11.40 µs 同量级。
- 语义按大类隔离，`BigBang` 的双重归属不会互相抵消，也不会随求值顺序变化。
- 多人限定卡的放行是构建期的固定规则，不占用豁免表，也不会被用户误配。

**代价**

- 索引必须随设置变更失效重建。实现上需要一个版本号或脏标记。
- 同一张卡在多个大类被豁免时，用户要在每处各勾一次。设置页必须提示「此卡还属于其他大类」。
- 豁免表本身需要持久化，与开关一起存进配置档。

**下游必须遵守的规则**

- 索引构建只允许读分组表、豁免表与卡牌的多人约束，不得读取任何随机数（SP-003）。
- 过滤后候选集合为空时按 SP-002 回退，回退路径不经过豁免。
- 多人限定卡的放行是硬规则，不得做成用户开关。
