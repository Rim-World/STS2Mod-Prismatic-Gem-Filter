# 002 三版本交付形态

- 状态：提议
- 日期：2026-11-15
- 当时的项目版本：0.0.0（仅文档）
- 相关文件：`1.PRD/001-项目初期需求.md`（RQ-004）、`2.PLANS/001-G-项目大纲.md`（P1、P5）

## 背景

用户要求同时兼容 0.107.1、0.111.0、0.113.1。约束如下：

- 愚者是 0.113 系列新增角色，0.107.1 与 0.111.0 中不存在对应的卡牌与卡池。
- 本机游戏目录只有 0.113.1 的程序集。参考资料库 `C:\Users\13167\Desktop\Mod\STS2-Reference` 存有 0.107.1、0.111.0、0.113.1 三个版本的完整反编译，比对本可以在本机完成。0.113.0 自 2026-11-15 起不再支持。
- 社区已有两种多版本做法。RitsuLib 用根桩程序集加 `compat/<版本>` 子目录，并用 `ritsulib-variants.manifest` 记录每个变体的哈希。RandomForeseer 用根桩加 `lib/` 下的版本子目录（本机为 `lib/0.13.20`）。两者都不依赖游戏提供变体切换，版本子目录名的含义未确认。

## 决策

先做单一程序集，源码只有一套。对随版本变化的对象用运行时探测：特性存在则用，不存在则跳过对应开关。

只有在 P1 取证表明某关键成员（`CardCreationOptions.CardPoolFilter`、`GetPossibleCards`、`PrismaticGem`、`CardTag` 的具体项）在旧版缺失且无法降级时，才拆出变体目录。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 立即拆三份构建加根桩加载器 | 在无旧版证据前拆分会浪费工作量，且加载器本身要维护 |
| 只支持 0.113.1 | 与 RQ-004 冲突 |
| 只用三个版本的交集 API | 交集要等取证结果，现在无法确定；且可能拿不到过滤所需的数据 |

## 后果

- 获益：取证前不锁定交付形态，改动成本低。
- 代价：运行时要处理成员缺失，代码里会出现分支与空实现。
- 代价：若最终拆变体，需要额外的加载器程序集与清单文件，打包变复杂。
- 下游规则：所有跨版本差异必须收敛到单一探测入口，不得散落在过滤逻辑里。该入口的形态在 P3 阶段确定后补写 SDD。
- 待补：本决策依赖 P1 的取证结论。取证完成前状态保持「提议」。
