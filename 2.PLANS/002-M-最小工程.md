## 目标

用最少的代码跑通一条链路：补丁能挂住、池门控有效、空集不炸、日志可读。

三件要验证的事：

1. 后置补丁能在本机 0.113.1 上改变 `CardCreationOptions.GetPossibleCards` 的返回集合。
2. 玩家本职业的牌不会被排除。
3. 过滤后集合为空时，发牌链路不抛 `InvalidOperationException`。

## 分步施工

每一步结束时都要能观察到结果，不通过则停下修正，不继续下一步。

### 第 1 步 建工程，编译出空壳

- 建 `PrismaticGemFilter.csproj`，引用 `sts2.dll` 与 `0Harmony.dll`。
- 加 `Plugin.cs`，只写一个 `[ModInitializer]` 入口，入口里打一行日志。

- **验证**：启动游戏，日志出现模组被加载的记录，主菜单模组列表能看到它。

### 第 2 步 接入 RitsuLib

- 读 RitsuLib 实际 API 签名。来源优先级：`mods\STS2-RitsuLib\shared\*.xml` 的 XML 文档注释，其次 `docs/pages/guide/patching-guide.md`。

- **验证**：日志出现 RitsuLib 已初始化，以及本模组的 patcher 已应用。

### 第 3 步 打空补丁

- 新增 `CardCreationPatch.cs`，目标是 `CardCreationOptions.GetPossibleCards(Player)`。
- 后置方法只打日志：候选数、玩家职业、是否持有棱彩宝石。原样返回。
- **验证**：进一局游戏，拿一次战斗奖励，日志出现三次（3 张牌各调一次）。

- `ExclusionTable.cs` 放 12 个奥斯提卡牌标识。

## 补丁细节

目标方法：

```csharp
public IEnumerable<CardModel> GetPossibleCards(Player player)
```

三版签名一致，见 [DOCS/008-E](../3.DOCS/008-E-三版本API对照.md) 第二节。

后置逻辑的判定顺序：

1. 玩家没有职业卡池信息，直接返回原集合。
2. 遍历候选牌，逐张判断：
   - 卡牌标识不在排除表内，保留。
   - 在表内，但该牌所属卡池等于玩家职业卡池，保留。
   - 在表内且不属于玩家职业卡池，排除。
3. 排除后若为空，返回原集合并打警告。
4. 否则返回过滤后的序列。

不需要显式判断玩家是否持有棱彩宝石。原因：未持有时候选集合只含玩家本职业卡池的牌，第 2 步的池门控会全部保留，过滤成为空操作。这与 SP-005 的验收标准一致。

## 补丁点的影响面

`GetPossibleCards` 在 0.113.1 共 5 处调用：

| 位置 | 用途 | 影响 |
|---|---|---|
| `CardFactory.cs:218` | 所有卡牌奖励的候选枚举 | 目标位置 |
| `BigGameHunter.cs:53` | 精英奖励探测「有没有稀有牌」，只取数量 | 池门控保证探测不空，实际无影响。见下节 |
| `LastingCandy.cs:125` | 遗物额外奖励的候选 | 与目标一致，属于遗物发牌 |
| `ScrollBoxes.cs:77` | 遗物奖励的候选 | 与目标一致 |
| `ScrollBoxes.cs:78` | 同上，第二个候选集合 | 与目标一致 |

`BigGameHunter` 是跑局修正器，只在「精英战后卡牌奖励」上生效。它调 `GetPossibleCards` 的目的只是探测「有没有稀有牌」，不消费候选。

池门控会让这类探测免于受本模组影响，理由见下一节。

第 4 步验证时专门跑一次精英奖励，确认行为与未装模组时一致。

## BigGameHunter 的探测为什么不构成风险

`MegaCrit.Sts2.Core.Models.Modifiers\BigGameHunter.cs:34-59` 的逻辑：

1. 四个早退条件：来源不是 `Encounter`、稀有度不是 `EliteEncounter`、带 `NoCardPoolModifications`、带 `NoRarityModification`。
2. 通过后把稀有度改为 `Uniform`，并加一个「只要稀有牌」的 `CardPoolFilter`。
3. 调 `GetPossibleCards(player).ToList()`，只取 `Count`。
4. `Count <= 0` 时，把卡池换回玩家本职业卡池。

第 3 步的探测走的就是本模组的补丁点。钩子顺序保证此时卡池已经加宽：`RunState.IterateHookListeners` 先放遗物，再放修正器（`RunState.cs:576` 起）。所以探测看到的是加宽后的候选集合。

但探测不可能被本模组清空。探测的集合是「加宽后卡池里的稀有牌」。池门控保证玩家本职业卡池的牌一律保留，其中有稀有牌。所以只要原版能探测到东西，本模组过滤后仍能探测到东西。

反过来，如果原版就探测不到稀有牌，说明加宽后确实没有稀有牌，此时本模组没有改变任何东西，回退照常发生，与未装模组一致。

结论：这一处不需要特殊处理。前提是池门控按 SP-004 正确实现。

**未确认**：一张牌同时属于多个卡池时，`CardModel.Pool` 返回哪一个。属性实现是对 `ModelDb.AllCardPools` 取第一个包含该牌标识的池（`CardModel.cs:359` 起）。若顺序把 Token 池排在角色池之前，池门控可能误判。第 4 步顺带抽查 10 张牌的实际 `Pool` 值。
